Если конфигурация удалена уже во время работающего сервера, запрос выдаст точную ошибку; скрытое изменение настройки во время игры не применяется.

# Установка

1. Опубликуйте `funcombat_server.rbxl` как серверный плейс своей игры. `Game_Server.rbxlx` — та же сборка в XML. Для обычной публикации откройте файл в Roblox Studio, настройте Avatar Type **R6**, затем Publish to Roblox. Публикация сервера не выполняется клиентским executor. Если Studio у вас недоступна, файл можно передать человеку с доступом к публикации вашего плейса.

   Используйте пересборку с serialization version 2. Первая версия бинарного файла имела неверный тип TeamColor и не открывалась в Studio. Замените старый файл из Downloads; соответствующие сервер и manifest должны иметь одинаковый новый build ID.

   Пересборка с исправлением спавна удерживает R6-тело во время загрузки внешности и размещает его на исходной карте до HTTP-запроса. После обновления откройте новый файл целиком: перенос только Script Main оставит старые ModuleScript и небезопасный StarterCharacter. Проверьте вход и Reset сначала без executor: карта и живое R6-тело должны появляться за счёт сервера. В случае ошибки откройте Studio Output; серверные предупреждения начинаются с FunCombat spawn / FunCombat avatar.

   Исправление карты дополнительно устраняет немедленный отказ `The original active map is missing`: WorldData задаёт имя оригинальной стартовой карты, а сервер при необходимости загружает её из своего исходного шаблона. Строка `FunCombat restored original map Crossroads from ServerStorage.FunCombatData.Maps` означает такое восстановление. При ошибке после 5 секунд Output перечислит фактические Workspace/Maps; это помогает отличить отсутствующие серверные данные от отсутствующего IsMap. Для успешного запуска ищите строку `FunCombat server ready` с актуальным build ID.

   Готовность персонажа подтверждается отдельно: `FunCombat character ready: <username>; Anchored=false`. CharacterAdded приходит до parenting модели, поэтому сервер ожидает её появления в Workspace, а затем снимает временную фиксацию. Проверьте WASD/прыжок и Reset без executor: базовое движение не зависит от loader.lua. Если этой строки нет, сохраните весь Server/Client Output; ожидание появления R6-модели ограничено 10 секундами, загрузки внешности — 8 секундами.
2. Содержимое `Game_GitHub.zip` соответствует корню репозитория. В опубликованном `FunCombatAssets` уже должны находиться `manifest.json`, `config`, `client`, `assets`, `loader.lua`, `Builder` и документация. Серверный файл и GitHub должны иметь один build ID.
3. В начале `loader.lua` находится единый блок CONFIG: Owner, Repository, Branch. В поставляемой сборке указаны реальные `a65407112-boop/FunCombatAssets`, ветка `main`. После обновления GitHub используйте отдельный `loader.lua` или raw-файл из репозитория.
4. Executor должен предоставлять `loadstring` и HTTP GET. Исходные оружия и костюмы восстанавливаются из JSON с тремя сохранёнными native UnionOperation, 11 MeshPart и одним SurfaceAppearance в новом серверном плейсе; `writefile`/`getcustomasset`/local `GetObjects` для них не требуются. Эти файловые функции остаются fallback для дополнительных model-пакетов без native-зависимостей. Настоящий executor здесь не тестировался.
5. Подключитесь к опубликованному серверу и запустите loader. Другие игроки также запускают внешний клиент, чтобы видеть клиентские оружия, костюмы, интерфейсы и эффекты. Серверное состояние синхронизируется через одинаковый протокол для всех клиентов.
6. Ошибка build ID означает, что сервер и репозиторий разных сборок. Ошибка HTTP/checksum означает отсутствующий файл, недоступную ветку или незавершённое обновление. Отсутствие original native CSG/MeshPart/SurfaceAppearance dependency означает неверный/старый серверный плейс. При ошибке bootstrap появляется окно с полным текстом, прокруткой и кнопкой Copy full error, если executor поддерживает clipboard. Полный текст также печатается в консоль. Бесконечного ожидания этих ресурсов нет.

Сборка 7 октября исправляет воспроизведённую ошибку PC Maxwell/PBR и сохраняет оригинальные mesh данные загрузки вместо Part/SpecialMesh. Она требует **публикации всего нового серверного файла**, а затем подключения к новой серверной сессии. Только обновление GitHub или перенос отдельных скриптов не добавит эти native-зависимости. После запуска проверьте Sword/Maxwell и оба костюма в своём клиенте; их рендер и размеры здесь не проверялись.

Запуск с реального репозитория:

```lua
loadstring(game:HttpGet("https://raw.githubusercontent.com/a65407112-boop/FunCombatAssets/main/loader.lua?t=" .. tostring(os.time())))()
```

Kohl’s Admin Infinite запускается сервером отдельно от executor. Ваш явно указанный UserId **11556197791** задан в единственном исходном файле `config/admin.json`: builder включает его в серверный Config и оригинальный Kohl Owners. Для Kohl это Owner (power 5); его исходная автоматическая creator/group-owner политика также сохранена. Встроенная панель и dummy bridge разрешают этому ID доступ независимо от результата lookup фактического владельца. Смена аватара или username не меняет numeric UserId. Изменение admin.json требует пересборки и публикации сервера; клиентская правка не выдаёт права. В Output смотрите `FunCombat admin access granted: userId=11556197791; source=configuredOwner` либо `source=publishedCreator`. После готовности ищите `FunCombat original Kohl's Admin ready; asset 1868400649`. Владельцу опубликованной пользовательской игры Kohl автоматически даёт creator rank; для игры группы это владелец группы. Неопубликованный CreatorId=0 не даёт автоматического creator grant, но явно настроенный реальный Player с указанным ID всё равно получает доступ к game controls. Обычные участники группы не получают доступ к новой dummy-команде или встроенной панели.

Будучи владельцем, введите в чат **`:dummy`**, чтобы создать боевой dummy перед собой. Для внешности по настоящему Roblox UserId используйте **`:dummy 261`** или нужный ID. Это исходный DummyRig, подключённый к серверному combat, а не локальная копия персонажа. Нужно быть живым и свободным от взаимодействия; cooldown 3 секунды, лимит 4 на игрока и 20 на сервер, настройка AllowDummys должна разрешать создание. Команда также доступна как `:spawndummy`. Hosted Kohl создаёт свою оригинальную UI/сеть и может зависеть от разрешений Roblox; полный hosted модуль не включён в zip.

Диагностика запускается **отдельно вручную**; основной loader её не вызывает. Она читает текущую голову, права сервера, числовой rank native Kohl и доступные ошибки даже после failed bootstrap. Ничего не переодевает и не меняет. Отчёт открывается в отдельном окне игры: нажмите **Copy report** и вставьте результат в чат. Консоль не требуется. Если executor не разрешает clipboard, та же кнопка выделит отчёт; используйте Ctrl+C либо мобильное меню копирования. Ошибка clipboard видна в окне. **Close** закрывает окно; повторный запуск заменяет предыдущее. После смены аватара перезайдите в новый сервер и запустите снова, чтобы получить актуальные данные:

```lua
loadstring(game:HttpGet("https://raw.githubusercontent.com/a65407112-boop/FunCombatAssets/main/diagnose.lua?t=" .. tostring(os.time())))()
```

Отправьте полный скопированный отчёт, если голова остаётся чёрной или Owner не отображается. Диагностика не утверждает, что успешный asset fetch означает успешный рендер. Для обновления только diagnose.lua перепубликовывать сервер не нужно. Если Roblox не разрешает ни один GUI container, скрипт сохраняет отчёт и точную GUI ошибку локально; такое ограничение самого executor здесь не подтверждено.

Управление из исходника: выбор оружия через оригинальный GUI; удар мышью/свободным касанием; Q — dash; G — восстановление после падения, когда сервер разрешает; G/H/J/K/L — исходные emotes. E/R/T и удержание сохраняются у соответствующих ProximityPrompt. R/мобильная R запрашивают следующий этап парного взаимодействия. `/e secretdoor` управляет исходной дверью Crossroads. Команды `spawn`, `d`, `sd`, `/s`, `/sd`, `/spawn` с необязательным userId создают оригинальный dummy; сервер ограничивает частоту и количество.

Обычный персонаж использует исходное R6-тело. Сервер получает одежду, цвета, настоящие head/face/mood Roblox-аватара по UserId. Dynamic heads включены; если R6 ApplyDescription не создал FaceControls, сервер запрашивает временный R15-модель с той же головой и переносит только его голову с FaceControls/Bones, сохраняя R6 шею и крепления волос. Ожидание подготовки внешности ограничено восемью секундами; отказ/timeout изолированного запроса головы сохраняет доступное R6-тело и сообщает конкретную причину. Если сервис недоступен или Studio использует тестовый UserId, внешность может остаться базовой. Сам выбор пола не загружает отдельный пользовательский костюм: config/outfits.json не содержит таких packages. Исходные LowerRig/TorsoRig и female InteractionFX внешний клиент применяет во время исходных парных взаимодействий.

Для этого обновления замените опубликованный серверный плейс и подключитесь к новому серверу, затем запустите актуальный loader. Старый сервер не соответствует новому build ID. Во время запуска загружаются все 129 оригинальных пакетов и 47 последовательностей анимаций шестью ограниченными workers; общий deadline bootstrap — 300 секунд. Отсутствующий обязательный ресурс останавливает запуск с именем файла. Hosted content получает дополнительное ограниченное ожидание; Failure/TimedOut выводят asset ID. Исходные игровые cooldown и сетевое время подтверждения действия сохранены.

Настоящие head/accessory/mood персонажей и user-ID dummy дополнительно готовятся асинхронно при появлении и смене ресурсов. Ожидание одного preload ограничено CONFIG.Timeout; поздние callbacks старого персонажа игнорируются. SurfaceAppearance использует обработанные Roblox texture packs, которые PreloadAsync не подтверждает. Чёрный рендер головы в опубликованном сервере пока не воспроизведён; успех bootstrap не доказывает корректный рендер. Сохранённая ошибка FunCombatAvatarDiagnostic появляется даже при позднем подключении клиента.

# Воспроизведение сборки

Python 3.11+, пакеты `Builder/requirements.txt`, **rbxmk 0.9.1**. Builder принимает этот конкретный исходник и проверяет SHA-256 до записи. Исходник должен находиться вне output. В полном архиве рядом с Builder находятся GitHub-проект и его инструменты.

```bash
python3 -m pip install -r Builder/requirements.txt
python3 Builder/build.py --source /absolute/path/FunCombat_Renamed2.rbxl --rbxmk /absolute/path/rbxmk --output /absolute/path/output
```

Из полного архива удобнее запускать `GitHub/Builder/build.py`: builder использует лежащий рядом репозиторий. Выход: два формата плейса, GitHub-папка, два zip, отдельный loader, метаданные и статические проверки. rbxmk выполняет сериализацию форматов, а не игровой тест Roblox.

Перед использованием проведите в Roblox тест двух игроков: загрузка и повторный запуск, позднее подключение, смена карты, все оружия, падение/восстановление, перенос/остановка/выход/респавн, обе финальные атаки, все парные варианты и Completions. Отдельно проверьте hosted assets и свой executor. Геометрическая инспекция в builder отсутствует.

Исправление WeldConstraint: внутренние XML-имена Part0Internal/Part1Internal нормализуются в доступные Luau Part0/Part1. Исходные endpoints сохраняются; оригинальный rbxl и экспорт rbxmx не изменены. Новый assets factory также понимает старые JSON с внутренними именами.
